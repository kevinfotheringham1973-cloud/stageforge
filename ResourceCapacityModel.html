StageForge — Resource Capacity Model

Technical scoping — Draft v0.1
Last updated: 19 Aug 2026
Source: PRD.html §06 "Resource & Capacity View" + DataModel.html §04 (ResourceAllocation sketch) + the decisions, 19 Aug 2026
Scoping — not built

Working out the shape of the "lowest-confidence scope item" in the whole system — PRD.html §06 gave it one sentence ("potentially a resource view"), and DataModel.html §04 sketched a single entity with no fields. This document turns that into something buildable.

01Starting boundary

Two things were already decided before this document existed, and both matter more than they look:

  • Current-state only. PRD.html §11 explicitly puts "resource/capacity forecasting beyond a simple current-state view" out of scope. This isn't a scheduling tool — it answers "who's over-allocated right now," not "who will be free in March."
  • The role already exists, unused. Resource / Portfolio Manager is one of the eight core roles (PRD.html §04: "Views resource allocation and capacity across live projects") and is seeded in roleDefs — but has zero assignments, zero actions, zero UI anywhere in the app today. This view is the first thing that role actually does something.
Decided Confirmed 19 Aug 2026: capacity is measured as % FTE per project (e.g. 40% allocated to Project A) — not days/week or hours/week. Sums per person across their live projects; over 100% is the over-allocation signal. Simplest unit that answers the actual question, no calendar or working-pattern data needed.
Decided Confirmed: only delivery-facing roles are tracked — PM, Authorised Person, Authorising Engineer, Principal Designer, and FM Contractor-side roles. Sponsor, SRO, and Compliance Officer sit outside this view; their oversight capacity isn't what "resource management" means in this context.

02What's already built and reusable

  • ProjectRoleAssignment already grants one User a Role on one Project — the "who's on what" fact this view reads. No schema change needed to know who's eligible to appear.
  • getCurrentUserGlobalRoleKeys() (added for provisioning, session.ts) is exactly the shape Resource Manager authority needs too — the role is inherently cross-project, same as it was for a Compliance Officer reviewing a draft with no project-scoped assignment yet.
Net-new work One new entity (ResourceAllocation) for the percentage itself, a place for a PM to set it, a place for a Resource Manager to view it aggregated, and a decision about which projects still "count" toward someone's total (§04 below — this turned out to be the least obvious part).

03Data model

Entity / fieldPurpose
ResourceAllocationNew model: id, userId, projectId, allocationPercent (Int), updatedById, createdAt, updatedAt. @@unique([userId, projectId]) — one live number per person per project, not a role-assignment-scoped or time-boxed value.
Decided Keyed by (User, Project), not by ProjectRoleAssignment. Someone can hold two roles on the same project (Derek Gibb is both PM and FM Contractor on the UPS example) — their time on that project is still one number, not one per hat worn. Keying to the assignment row would double-count them in every portfolio sum.
No time period, no history table beyond the usual AuditLogEntry row on change (resource.allocation_updated) — a straight overwrite. Adding periods would be the first step toward forecasting, which §01 rules out for this pass.

04The gap this scoping pass actually found

Nothing in the source material addresses this, and it matters more than anything else here: StageForge has no concept of a project being "finished." Project.status only has DRAFT and ACTIVE (added for provisioning) — there's no COMPLETE/CLOSED state. A project stays ACTIVE forever, even once every gate is SIGNED_OFF.

Left unaddressed, a "current-state" resource view would permanently over-report everyone's allocation — a PM's 40% on a project finished eight months ago would still count toward their total today, with no way for it to ever drop off.

Recommendation Don't add a new Project.status value for this. Derive it from data that already exists: a project only counts toward the resource view while at least one of its Gates is not yet SIGNED_OFF. Once every included gate is signed off, the project drops out of everyone's live-allocation total automatically — no new field, no migration for existing data, and it's exactly the same signal the rest of the app already treats as "this project is actually moving" (e.g. the project overview's isCurrent highlight logic).
Open question This still leaves the general "does StageForge model project completion at all" question open beyond this one view — e.g. should a fully-signed-off project stop appearing in normal project listings too, once those exist? Out of scope for this document; flagged for whoever builds a project list/portfolio page next.

05Who sets the number, who views it

ActionWhoWhere
Set/update a person's allocationPercent on a projectPM (of that project — project-scoped, same as every other PM action in the model)New control on the existing project overview page (/projects/[projectNumber]), next to each delivery-facing role holder already shown there.
View aggregated allocation across all live projectsResource / Portfolio Manager (global — no single project owns this view, same reasoning as Compliance Officer's draft-review authority in ProvisioningModel.html)New route, e.g. /resources — a flat table: one row per tracked person, their summed %, a per-project breakdown, over-100% highlighted.

Read-only for the Resource Manager, matching PRD.html §04's exact wording ("Views resource allocation") — they see the picture, they don't edit individual numbers. If two PMs' numbers add up to an over-allocated person, resolving that is a conversation between PMs, not an edit the Resource Manager makes unilaterally.

06Explicitly out of scope here

  • Forecasting, future-dated allocations, or anything calendar-shaped (§01).
  • A pool of "available but unassigned" people — the system only knows about Users who already exist and already hold a ProjectRoleAssignment somewhere. There's no roster of a company's total headcount to compare against.
  • Sponsor/SRO/Compliance Officer capacity (§01 decided).
  • Any automatic rebalancing or suggestion — the view surfaces over-allocation, it doesn't resolve it.

07Open questions

  1. Whether a fully-signed-off project should eventually get a real completion marker rather than the derived "all gates signed off" signal used here (§04) — revisit once a project list/portfolio page exists and needs the same signal.
  2. Whether a PM should be able to set allocation for a person who isn't yet at 100% total review-worthy, i.e. should the UI warn at the point of setting a number that would push someone over 100%, or only surface it later in the Resource Manager's view? Leaning toward warn-at-entry (cheaper to catch), not decided.
