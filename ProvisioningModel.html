StageForge — Provisioning Model

Technical scoping — Draft v0.2
Owner: Kevin Fotheringham · 19 Aug 2026
Source: PRD.html §06 "AI-Assisted Project Provisioning" + Kevin's decision, 19 Aug 2026
Scoping — not built

How a new project actually gets its deliverables checklist, compliance requirements, and PM guidance from a short description — the mechanism behind PRD.html §06, worked out to the level DataModel.html and ConfigSchema.html worked out the Compliance Module before it got built.

01Scope decision

PRD.html §06 described the goal without committing to a mechanism. Two shapes were on the table:

Template-library selection — chosen
  • An LLM call reads the project description and matches it against a growing library of pre-authored Templates (the same Template → StageTemplate → GateTemplate → DeliverableTemplate shape already in the schema).
  • The LLM's job is matching and light adaptation — picking the closest template and extracting Project.tags — never inventing checklist items from scratch.
  • Bounded failure mode: worst case is picking the wrong (but still human-authored, still real) template. Never a hallucinated deliverable.
Freeform generation — rejected for now
  • An LLM drafts a brand-new checklist from scratch each time, no library needed.
  • More flexible, matches the more ambitious reading of the PRD text literally.
  • Unbounded failure mode: a hallucinated or incomplete regulatory checklist, in a system whose entire value proposition is compliance accuracy. Rejected on that basis.
Decided Confirmed by Kevin, 19 Aug 2026: template-library selection. Everything below is scoped to that shape.

02What's already built and reusable

This isn't starting from zero. Two pieces of existing, shipped work carry almost all of the load:

  • The RIBA 8-stage structure is fixed, not generated. Every Health-sector project runs Strategic Definition → Use regardless of what it's for (PRD.html §06 decided flag) — so provisioning never needs to invent stages or gates, only what fills them.
  • The compliance merge mechanism already does the hard part. matchingComplianceRuleTemplates (app/src/lib/compliance.ts) already matches ComplianceRuleTemplates onto a Gate at Stage instantiation, driven entirely by Project.tags. Once provisioning can produce a correct tag set from a description, compliance instantiation needs zero new code — it already runs the same way for a reinstated stage or a seeded project.
Net-new work What's actually missing is narrower than it first looks: (a) more than one Template to choose between — today there's exactly one, "M&E Systems Replacement", (b) matching metadata on each Template for an LLM to match against, (c) an actual "create project" flow — Phase 1 has never had one; every project so far came from seed.ts, (d) the LLM call itself, and (e) a review step before a provisioned project goes live.

03The provisioning flow

1
Input. PM or Compliance Officer enters a free-text project description, e.g. "Replace 12 UPS units across 4 systems, weekend working, live hospital."
2
Match. One LLM call, given the description plus every candidate Template's matching metadata (§04) and the full list of known compliance tags, returns: the best-matching templateId, a confidence/reasoning note, and a proposed Project.tags set.
3
Draft. A Project row is created in DRAFT status (§04) — not yet visible to a PM as a working project — carrying the original description, the chosen template, and the proposed tags, but stages/gates are not instantiated yet.
4
Review. A Compliance Officer reviews the match: right template? right tags? Can edit the tags, can override the template choice, or reject and re-run with a clarified description.
5
Activate. On approval, the project flips to ACTIVE and instantiation runs exactly like today's seed/reinstate path: every StageTemplate → Stage, every matching DeliverableTemplate and ComplianceRuleTemplate → live Deliverable/ComplianceRequirement rows. No new instantiation logic — this calls the existing code.
Decided Confirmed by Kevin (this session): a generated project requires Compliance Officer review before going live — resolves the open question PRD.html §06 left open. This also matches the existing rule that template/rule-set authoring is Compliance Officer-only (ConfigSchema.html §06); reviewing a provisioning match is the same authority tier as authoring the content it draws from.

04Data model

Nothing here touches DeliverableTemplate, ComplianceRuleTemplate, Stage, Gate, or Deliverable/ComplianceRequirement — instantiation itself is untouched, only what happens before it runs.

Entity / fieldPurpose
Template.description, Template.matchKeywordsShipped (19 Aug 2026, PR #9). What the LLM matches a project description against.
Project.statusNew enum ProjectStatus { DRAFT, ACTIVE }, @default(ACTIVE) — every existing/seeded/reinstated project is unaffected, since only the provisioning path ever sets DRAFT. A DRAFT project has no instantiated Stages/Gates yet.
Project.createdByIdNew — who authored the draft (currently nothing on Project tracks this). Needed to know who's allowed to revise the brief; no existing field covers it.
Project.provisioningBriefThe free-text description. Editable while DRAFT (§05, reviseProvisioningBrief) — each revision re-runs the match.
Project.provisioningMatchReasoningThe LLM's stated reasoning for its current match, shown to the reviewer. Overwritten each time the match re-runs — it describes the current proposal, not a history.
ProvisioningReviewNew model. The human decision history for a project's provisioning: id, projectId, decision (APPROVED | REVISE), reviewedById, reason, createdAt. Deliberately shaped like GateSignOff — no flat "reviewedBy/reviewedAt" columns on Project itself, same reasoning as why Gate has no such columns either: read the latest row instead of duplicating state.
Decided No REJECTED terminal status — mirrors the existing GateSignOff pattern exactly (PRD.html §06 Stage-Gate Engine: rejection returns a gate to IN_PROGRESS with a reason, never a dead end). A Compliance Officer sending a draft back for revision is a ProvisioningReview(REVISE, reason) row; the Project simply stays DRAFT, editable, not deleted or archived.

05Actions & permissions

ActionWhoEffect
createProvisioningDraftPM or Compliance OfficerCalls the LLM match (§07) against the free-text brief; creates the Project as DRAFT with the proposed templateId/tags/reasoning. No Stages/Gates yet.
reviseProvisioningBriefThe drafting PM only (createdById)Edits provisioningBrief, re-runs the match, overwrites the proposed template/tags/reasoning. Same Project row — no new project number.
updateProvisioningDraftCompliance Officer onlyDirectly overrides the proposed templateId/tags without re-running the LLM — the reviewer just knows better. Same authority tier as authoring template content (ConfigSchema.html §06).
requestProvisioningRevisionCompliance Officer onlyReason required (same mandatory-reason pattern as every override/bypass/rejection in the model). Records ProvisioningReview(REVISE, reason). Project stays DRAFT.
approveProvisioningCompliance Officer onlyRecords ProvisioningReview(APPROVED), instantiates every included Stage/Gate from the final templateId (§06), sets status: ACTIVE.

Every action also writes the usual AuditLogEntry — project.provisioning_drafted, project.provisioning_revised, project.provisioning_revision_requested, project.provisioned — same append-only trail as everything else.

Open question Role assignment. A real project needs a PM, Sponsor, SRO, Compliance Officer, FM Contractor, and Client Authority (§04 of PRD.html) — createProvisioningDraft only settles the creator as PM. Whether the rest get assigned as part of the creation form, during review, or in a separate step afterward isn't decided here.
Open question Stage inclusion. Every seeded/reinstated project today sets includedStageKeys deliberately (the UPS example excludes Gate 7/Use). Provisioning could default to all 8 stages and let the PM exclude some before or during review — simplest for v1, but not decided as the final answer.

06Reusing the instantiation logic

approveProvisioning's instantiation step — Stage/Gate creation, copying DeliverableTemplate rows to live Deliverables, calling matchingComplianceRuleTemplates for the compliance merge — is not new logic. It's what reinstateStage (app/src/lib/actions.ts) already does for one stage at a time, and what seed.ts does for every stage of a new project at once.

Recommendation Extract a shared instantiateStage(db, project, stageTemplate) helper (alongside matchingComplianceRuleTemplates in app/src/lib/compliance.ts, or a new app/src/lib/instantiation.ts) before building approveProvisioning — today the same Stage/Gate/Deliverable/ComplianceRequirement creation sequence is written out inline in two places (reinstateStage and seed.ts's loop); a third copy for provisioning would be the point it stops being a coincidence and starts being a maintenance liability. approveProvisioning then just calls this once per included stage, same as reinstateStage calls it once.

07The LLM call

  • One call per provisioning attempt — matching plus tag extraction in a single structured-output request (template id + tags + a short reasoning string shown to the reviewer), not a multi-turn conversation.
  • Deterministic-leaning: low temperature, since this is a matching task against a closed set of templates and a closed set of known tags — not open creative generation.
  • The reviewer sees the model's stated reasoning alongside its picks, so a wrong match is inspectable, not a black box.
  • Called from both createProvisioningDraft (first match) and reviseProvisioningBrief (re-match after a revision) — one function, two call sites.
Open question Which model/provider, and where the API key/cost sits — infra decision, not a data-model one, deferred to implementation time.
Decided The library now has two Templates (19 Aug 2026, PR #9) — the "match step is trivially always correct" concern from the previous draft of this document no longer applies. §05/§06 above can be built for real, not just as unreachable plumbing.

08Open questions carried forward

Consolidated from §05–§07 above, plus one from the review flow itself:

  1. Role assignment at draft/approval time — who assigns Sponsor, SRO, FM Contractor, Client Authority, and the rest beyond the creating PM.
  2. Stage inclusion — default to all 8 RIBA stages, or let the PM exclude some at creation/review time.
  3. LLM provider/model and API key/cost ownership.
  4. Whether updateProvisioningDraft (silent reviewer override) and requestProvisioningRevision (send back to the PM with a reason) are both genuinely needed, or whether one subsumes the other in practice — kept both here since they serve different situations (reviewer knows the fix vs. reviewer needs the PM to clarify), but worth revisiting once there's real usage to observe.

09Explicitly out of scope here

  • Freeform deliverable generation (§01 — rejected).
  • Authoring UI for new Templates/DeliverableTemplates/ComplianceRuleTemplates themselves — still hand-authored in seed.ts for now, same as today. Provisioning selects among templates; it doesn't help create them.
  • Per-gate ongoing PM guidance (PRD.html §06's other open question — one-time brief vs. resurfaced per gate). Assume one-time brief, shown at Stage 0, for a first version; revisit if that's not enough.
