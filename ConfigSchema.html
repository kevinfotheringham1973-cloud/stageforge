StageForge — Config Schema

Draft v0.4 — companion to PRD v0.8 & Data Model v0.5
Last updated: 18 Aug 2026
Draft — schema not final

The config schema for Stage/Gate/Deliverable templates and Compliance rule sets — the two libraries the PRD's compliance-architecture recommendation asked to be built on one shared primitive, rather than as two separate subsystems.

01One primitive, two libraries

Every checklist item on a gate — whether it's a delivery deliverable or a compliance requirement — is the same shape: a label, an evidence requirement, and a flag for whether it blocks the gate. What differs is who maintains it and who can clear it without evidence:

  • Delivery checklist items live inside a StageTemplate, maintained per programme type. Cleared normally with evidence, or bypassed — by a PM for an ordinary item, or by Compliance Officer/SRO for one flagged legally significant.
  • Compliance checklist items live inside a ComplianceRuleSet, maintained per sector/jurisdiction, independently of any one programme template. Cleared normally with evidence, or overridden by an SRO.

They share one schema — ChecklistItemTemplate — so a Compliance Officer editing a rule set is filling in the same fields a PM would when building a delivery checklist, not learning a second system.

02The shared primitive

FieldTypeNotes
keystringStable identifier. Never changes once a live Project has instantiated it.
kind"delivery" | "compliance"Determines the default escape hatch: bypass for delivery, override for compliance.
labelstringShown to the PM and Sponsor on the checklist.
descriptionstring, optionalInstructions or context for whoever has to satisfy it.
rule_refstring, optionalCompliance items only — citation of the regulation or standard, e.g. "HTM 05-03". Free text, for traceability.
evidence_type"file_upload" | "attestation" | "external_check"file_upload is the default. attestation is a signed statement with no file. external_check is reserved for the rare case the PRD flagged as needing real logic — a live call to an external system — rather than pure config.
min_filesintegerDefault 1. Only meaningful when evidence_type is file_upload.
blocks_gatebooleanDefault true for both kinds — matches the PRD decision that compliance blocks on par with delivery evidence.
bypass_authority"pm" | "compliance_officer" | "sro" — delivery onlyWho's allowed to bypass this specific item. Default "pm". Set to "compliance_officer" or "sro" when the deliverable is legally significant — a PM cannot bypass those, by design.
applies_if_tagsstring[], optionalProject must carry at least one matching tag for this item to be included ("any match" — see §04). Empty or absent = always applies.

03Stage / Gate templates

Grounded in real UK public-sector capital governance terminology, since that's the domain: stages and gates modelled on the OGC Gateway Review structure already familiar to NHS capital programmes.

Note what's not here: no compliance items. A Compliance Officer never edits a StageTemplate to add a regulatory requirement — that would put regulatory content back under programme-template ownership, the exact coupling the config-driven recommendation was meant to avoid.

04Compliance rule sets

A rule set is maintained independently and attaches to stages by key, not by nesting — so the same rule can apply across every programme type that includes that stage, without being copy-pasted into each template.

compliance_rule_set — health sector, fire safety 
{
  "key": "compliance.health.fire_safety",
  "sector_variant": "health",
  "name": "Fire Safety & HTM 05 Compliance",
  "rules": [
    {
      "key": "comp.htm05_fire_risk_assessment",
      "kind": "compliance",
      "label": "Fire risk assessment current and on file",
      "description": "Required wherever works affect a compartment boundary or means of escape.",
      "rule_ref": "HTM 05-03",
      "evidence_type": "file_upload",
      "blocks_gate": true,
      "applies_to_stage": ["stage.design_planning", "stage.construction"],
      "applies_if_tags": ["acute_hospital"]
    }
  ]
}

applies_to_stage and applies_if_tags only exist on compliance items, not delivery ones — delivery items are already stage-scoped by where they're nested in the StageTemplate. Compliance items need it explicitly because one rule set is meant to be reused across many stage templates and programme types at once.

How tags work

applies_if_tags is deliberately simple: a Project carries a set of tags (e.g. acute_hospital, listed_building, occupied_during_works), and a rule applies if at least one of its tags matches. This is the whole extensibility mechanism the PRD asked for — a Compliance Officer adds a new rule with a new tag combination, no code, no deploy.

DecidedConfirmed: "any match" is sufficient for the sectors currently in scope — no AND/OR/NOT logic for now. Worth revisiting only if a future sector's rules genuinely need combined conditions rather than a single qualifying tag.

05How the two merge into a live Gate

At the moment a Stage is instantiated on a Project, its Gate's checklist is assembled once from both sources — the StageTemplate's delivery items, plus every rule in the Project's sector ComplianceRuleSet(s) whose applies_to_stage and applies_if_tags match. The result is copied into real Deliverable and ComplianceRequirement rows for that Gate.

Recommendation Copy at instantiation rather than resolving templates live on every read. If a Gate's checklist were computed fresh from the templates each time, editing a ComplianceRuleSet could silently change the requirements on gates that are already in progress or even signed off — which breaks the audit trail's claim that a sign-off reflects what was actually reviewed at the time. Freezing a copy at instantiation means template edits only affect future stages, never rewrite history on live ones. This wasn't explicitly asked for but follows directly from the audit-trail requirement already locked into the PRD.

06Authoring & project scoping

Two different permissions, easy to conflate: who can edit the shared template content, and who can decide how much of it a given project actually uses.

Decided Confirmed: authoring live edits to a StageTemplate or ComplianceRuleSet is restricted to Platform Admin and Compliance Officer. A PM never edits template content directly — consistent with a PM not being able to unilaterally change what's legally required of a project.

But not every project needs every stage a template defines — a small works order might not go through stages a full capital scheme does. Worth flagging: the PM needs some control here, just not over the template itself.

Decided Confirmed: a PM can select which subset of a StageTemplate's stages apply to their specific Project — scoping, not authoring. Modelled as Project.included_stage_keys, chosen at project setup. Absent, or containing every key in the template, means the full template applies unchanged.
Decided Confirmed: included_stage_keys is editable, not write-once — a PM can reinstate a previously-excluded stage later if scope grows mid-programme. Reinstating one instantiates its Stage and Gate at that point, using whatever the template and matching compliance rules look like at that moment — same "copy at instantiation" behaviour as any other stage, just triggered later.
excerpt — a Project scoped to a subset of its StageTemplate 
{
  "project_number": "20456",
  "stage_template_key": "template.health.ward_refurbishment",
  "included_stage_keys": [
    "stage.business_case",
    "stage.design_planning",
    "stage.construction"
  ]
}

This project simply never instantiates whatever other stages the template defines — e.g. a "Post-Occupancy Review" stage a larger scheme would carry. Compliance items still attach by applies_to_stage as normal; a rule scoped to an excluded stage never gets instantiated for this project either, the same as any other stage that isn't part of it.

DecidedConfirmed: a reinstated stage appends after the project's current point, rather than inserting back into its original template position. Simpler and safer — reinstating a stage never reshuffles or reopens stages that are already underway or complete.

07Open questions
